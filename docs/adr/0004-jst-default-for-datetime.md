# ADR 0004: 日時の扱いは日本時間（JST）をデフォルトとする

- ステータス: Accepted
- 日付: 2026-07-12
- 関連: ADR 0001

## コンテキスト

Cube Voyage は日本語のスピードキューブ情報サイトで、運営者は日本時間を前提に開発・運用を行っている。
しかし実際のコードは以下の点で UTC 基準になりうる。

- 開発・ビルドを実行する Node.js プロセスのタイムゾーンはホスト環境依存で、CI やコンテナ環境では
  デフォルトで UTC になりうる。
- Cloudflare Workers ランタイムは仕様上 `Date` / `Intl` が常に UTC で動作し、環境変数 `TZ` の影響を受けない。
- `/admin/analytics`（ADR 0001）の日別集計は D1 の `date(ts, 'unixepoch')` で日付を区切っており、
  これは UTC の暦日で区切られる。日本時間の 0:00〜8:59（UTC 前日 15:00〜23:59）のアクセスが
  前日分に混入し、運営者が体感する「今日の PV」と一致しない。

## 検討した選択肢

1. **現状維持（UTC 基準）** — 運営者が日本時間で確認する用途に合わず、日別集計が実際の日付とずれる。却下。
2. **すべての日時をアプリケーション層で JST に変換して保存する** — 保存形式が複雑化し、
   ADR 0001 の「UTC unix epoch 秒で保存する」というシンプルな設計の利点を失う。却下。
3. **保存は UTC unix epoch 秒のまま、表示・集計時にのみ JST へ変換する（採用）**。
   開発・ビルド環境は `TZ=Asia/Tokyo` をデフォルト化する。

## 決定

- **原則**: 開発・運用で日時を扱うときは日本時間（Asia/Tokyo, UTC+9）をデフォルトとする。
- **開発・ビルド**（`npm run dev` / `npm run build` / `npm run deploy`）: `TZ=Asia/Tokyo` を明示的に設定し、
  Node.js プロセスの `Date` を日本時間で解釈させる。静的ビルド時に評価される日付
  （例: `Footer.astro` の著作権年）はこれで日本時間になる。
- **Cloudflare Workers ランタイム**（SSR: `/api/hit`, `/admin/analytics`）: ランタイムは常に UTC で
  動作し `TZ` は効かない。D1 に保存する `ts` は引き続き UTC unix epoch 秒のまま保持し、
  JST への変換は読み出し・集計クエリ側で行う（例: `date(ts, 'unixepoch', '+9 hours')`）。
- **`/admin/analytics`**: 日別ページビューの日付区切りを JST に変更した。24 時間 / 7 日 / 30 日の
  相対集計（`unixepoch() - N`）はタイムゾーンに依存しないためそのまま UTC 基準の計算で問題ない。

## 影響

### 良い点

- 運営者が確認する日別集計・ログの日付境界が日本時間の体感と一致する。
- D1 の保存形式（UTC unix epoch 秒）は変えないため、既存データ・スキーマへの影響がない。

### 割り切り・コスト

- Cloudflare Workers ランタイムは UTC 固定という制約上、`TZ` 環境変数は開発・ビルド時のみ有効。
  ランタイム（SSR）で日付を扱う箇所は個別に JST 変換を書く必要があり、書き忘れると UTC 基準に戻る。
- 今後日時を扱うコードを追加する際は、この原則（保存は UTC、表示・集計は JST 変換）に従うこと。
